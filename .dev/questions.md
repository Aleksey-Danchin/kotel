## Q19 — Уточнение к Q4: SHA256 vs SHA512

SHA256 **не устаревает** и не будет устаревать в обозримом будущем. Ситуация:

- **MD5** и **SHA-1** — сломаны (найдены практические коллизии). Это упоминает и AUTH_DESIGN.md.
- **SHA-256** — ни одной практической или теоретической уязвимости. Используется в: Bitcoin, TLS 1.3, PKCE (RFC 7636 требует именно SHA-256), подписи сертификатов, HMAC. NIST рекомендует минимум до 2030+.
- **SHA-512** — та же семья (SHA-2), длиннее, но не «безопаснее» для данного сценария. Для токенов с 256-бит энтропией (из `crypto.randomBytes(32)`) SHA-256 даёт полную pre-image resistance (2²⁵⁶).

SHA-512 быстрее на 64-битных процессорах, но это не аргумент — разница в наносекундах.

AUTH_DESIGN.md в разделе PKCE явно использует SHA-256. Использование SHA-256 для хэширования токенов было бы консистентно со всем документом.

**Варианты:**
- a) SHA-256 — стандарт индустрии, консистентно с PKCE, полностью достаточен
- b) Оставить SHA-512 как в первоначальном ответе
- c) Другое: ___

**Ответ:** SHA-256 — стандарт индустрии, консистентно с PKCE, полностью достаточен

## Q20 — Уточнение к Q9: Deep Link схема — подробное объяснение

Объясняю три варианта:

### Вариант 1: Custom URL Scheme (рекомендуемый AUTH_DESIGN.md)

Это когда приложение регистрирует **свою** схему URL на уровне ОС, например `kotel://auth/callback`.

Настройка в Expo (`app.json`):
```json
{ "expo": { "scheme": "kotel" } }
```

Когда сервер редиректит на `kotel://auth/callback?code=...&state=...`, ОС перехватывает URL и открывает приложение. В Expo это работает через `expo-linking`:
```javascript
import * as Linking from 'expo-linking';
const redirectUri = Linking.createURL('auth/callback');
// В dev: exp://192.168.x.x:8081/--/auth/callback
// В production build: kotel://auth/callback
```

**Плюсы:** просто, работает на iOS и Android, Expo handle'ит различия dev/prod.
**Минусы:** на Android любое приложение может зарегистрировать `kotel://` и перехватить callback. Но AUTH_DESIGN.md обосновывает почему это не проблема — `code` без `codeVerifier` бесполезен.

### Вариант 2: Universal Links / App Links (HTTPS-схема)

Например `https://kotel.localhost/mobile/callback`. ОС верифицирует владельца домена.

**AUTH_DESIGN.md явно отклоняет** этот вариант: «требует привязки к конкретному `package_name` и сертификату — несовместимо с open source моделью».

### Вариант 3: Expo AuthSession (встроенный механизм)

`expo-auth-session` — обёртка поверх `expo-web-browser`, которая автоматически обрабатывает redirect. Но она навязывает свою схему URL и flow, что может конфликтовать с нашей кастомной OAuth реализацией.

---
