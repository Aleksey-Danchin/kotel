# Designer Sandbox (`apps/designer`)

## Purpose
`apps/designer` — песочница для разработки UI/UX и верстки. Это “дизайнерский слой” поверх структуры `app/frontend`: здесь можно быстро прототипировать интерфейс и имитировать поведение, не связываясь с backend.

## Isolation from environments
- `apps/designer` **не включается** в обычные `dev`/`test` окружения проекта.
- Запуск дизайнерской песочницы предполагается **отдельно** (как самостоятельный Vite-проект).
- Работы по UI в `designer` всегда рассматриваются как обособленные: не предполагаем наличие/доступность backend-стеков, контрактов и инфраструктуры main-приложения.

## What belongs here
- UI composition (routes, components, layouts)
- Визуальные сценарии и “ручные” макеты страниц
- Моделирование общего UI-state (граф `jotai`)

## What must NOT belong here
- Реальная бизнес-логика и интеграции с backend
- OAuth/token exchange, real auth refresh/coordination
- Calls to backend endpoints, которые нужны для корректности доменной логики
- Соглашения/валидации/контракты как часть runtime-backend (это живёт в backend/контрактных артефактах)

## Mock data rules
Если в песочнице нужны фейки (списки серверов, статусы, пользователи, sessionId и т.п.), они должны объявляться:
- в теле компонента (внутри функции компонента, где рендерится UI), либо
- во вкладках, которые принадлежат компоненту: event handlers / `useEffect` / `useMemo` внутри компонента.

Запрещено держать mock-объекты на уровне модуля (top-level), как “глобальную истину”.

## Jotai как часть дизайна
`jotai` — часть “дизайн-слоя” песочницы.

### Концепция
В `apps/designer/src/state/**` проектируется **граф атомов/сторов**, который:
- используется UI на уровне нескольких страниц/разделов,
- может подразумевать persist (тогда persist должен быть отражён в атомах),
- выступает как **дизайнерский контракт** для того, как frontend в дальнейшем будет расширять UI.

### Наследование для `apps/frontend`
`apps/frontend` может обогащать поведение, но должен **inherit** тот же атомный граф из `apps/designer`:
- не переопределять базовые atoms/stores,
- не дублировать “один и тот же” state в другом месте,
- добавлять только то, что расширяет UI (и по договоренности — сначала в designer, затем в frontend).

## Типовая структура
- `apps/designer/src/routes/**`: страничные компоненты (UI)
- `apps/designer/src/components/**`: переиспользуемые UI-компоненты
- `apps/designer/src/state/**`: общий `jotai`-граф (design contract)
- `apps/designer/src/global/**`: общие UI-утилиты, не содержащие business/runtime интеграций

## Трёхколоночный чат-шелл (верстка)

Стабильные решения по flex-шеллу, скроллу и визуальной иерархии сообщений зафиксированы в **[`docs/designer-chat-styling.md`](./designer-chat-styling.md)**. При изменении этих соглашений обновляйте этот документ и правила `.cursor/rules/designer.mdc` / `frontend.mdc` в том же изменении.

## Checklist перед коммитом в `designer`
- Нет реальных запросов к backend (нет `fetch`/`axios` к бизнес-эндпоинтам)
- Mock-данные объявлены внутри компонентов/обработчиков, а не как модульные константы
- Если состояние используется между страницами/разделами или предполагается persist — оно описано через `jotai` в `src/state/**`
- Если запрос “про бизнес-логику” — мы не делаем это в `designer`, а перенаправляем туда, где ей место
